# Оптимизация производительности: Как мы достигли 3 млн INSERT/sec

## Введение

В ранних или неоптимизированных версиях тестов база данных показывала порядка 100 000 – 115 000 операций вставки в секунду (RPS). После проведения комплексного профилирования и ряда оптимизаций базовая производительность хранилища **увеличилась почти в 30 раз**, достигнув отметки в **~3.14 миллионов RPS** на стандартном железе (без Write-Ahead Log).

С интеграцией полноценных ACID-транзакций, журналирования (WAL) и продвинутого механизма **Fuzzy Checkpointing** база выдает **~2.2 миллиона RPS**. Это невероятный результат, учитывая, что данные теперь на 100% защищены от сбоев питания, а чекпоинты происходят в фоне без остановки базы!

В этом документе подробно разбираются ключевые архитектурные решения и оптимизации, которые позволили `RawDB` летать на таких скоростях.

---

## 1. Пакетная вставка (Batched Inserts)

**Проблема:** Изначально в бенчмарке (`sql_bench.cpp`) каждая строка вставлялась отдельным SQL-запросом (`INSERT INTO t VALUES (1);`). Это означало, что для 100 000 строк база:
1. 100 000 раз вызывала парсер (`Parser::parse()`), который разбирал строку посимвольно.
2. 100 000 раз вызывала диспетчер `Executor::execute()`.

**Решение:** Мы перешли на использование множественной (пакетной) вставки:
`INSERT INTO t VALUES (1), (2), ..., (1000);`

**Эффект:** Накладные расходы на парсинг SQL-кода упали в 1000 раз. Парсер разбирает запрос один раз, а `Executor` получает уже готовое AST дерево с массивом из 1000 строк.

---

## 2. Исключение аллокаций в цикле (Zero-Allocation)

**Проблема:** Внутри метода `Executor::execute_insert()` для каждой вставляемой строки создавались временные векторы `std::vector<std::byte> bufs`. Выделение памяти в куче (`malloc`/`new`) — крайне дорогая операция. Вставка миллионов строк приводила к миллионам обращений к аллокатору ОС.

**Решение:** Мы вынесли векторы за пределы цикла и стали их переиспользовать с помощью `.clear()`:
```cpp
// Память выделяется один раз
std::vector<std::vector<std::byte>> bufs(schema.column_count());

for (const auto &row : stmt.rows) {
    for (size_t ci = 0; ci < row.size(); ++ci) {
        bufs[ci].clear(); // Очищаем вектор (O(1)), но capacity сохраняется!
        // ... запись данных ...
    }
}
```

**Эффект:** Устранено "бутылочное горлышко" аллокатора памяти. Процессор теперь работает исключительно с горячим кэшем (L1/L2), копируя данные без задержек.

---

## 3. Отложенная пакетная запись (PendingBatch) и Mmap

Даже с быстрым парсером запись на диск могла бы всё испортить. Но архитектура `RawDB` спроектирована иначе:
1. **PendingBatch:** Внутри класса `Table` есть буфер `pending_`. Вызов `insert_row` не инициирует запись на страницу немедленно. Данные просто добавляются в `std::vector` внутри оперативной памяти.
2. **Амортизация IO:** Запись целого блока данных на саму страницу происходит только когда буфер заполняется до `kBatchSize` (8192 строки). 
3. **Mmap:** Запись на саму "страницу" — это просто копирование в память (memory-mapped file). Мы делегируем реальный сброс данных на диск операционной системе (Page Cache), поэтому база вообще не блокируется на системных вызовах `write()`.

**Эффект:** Метод `insert_row` работает за время амортизированного `O(1)`, практически сводясь к обычному `memcpy`.

---

## 4. Как обстоят дела с остальными метриками?

Остальные показатели бенчмарка тоже на феноменальном уровне, потому что ядро БД спроектировано без лишних накладных расходов:

* **Полнотабличное сканирование (SELECT Fullscan): `9.65 млн строк/сек`**
  Исключительная скорость за счет того, что данные колоночно лежат в `mmap`, и сканирование идет линейно по памяти.
* **Поиск по индексу (Index Lookup): `1.74 млн запросов/сек`**
  B-Tree индекс в паре с `VersionIndex` отрабатывает за `~0.57 микросекунды` на запрос.
* **Сборка мусора MVCC (Version Index Prune): `1 млн записей за 3.4 мс`**
  Очистка старых версий (tombstones) происходит с колоссальной скоростью, что крайне важно для базы, которая обновляет данные через паттерн `DELETE + INSERT`.

---

## Итог

Сочетание **Mmap-хранилища**, **пакетного выполнения** и **оптимизации аллокаций памяти** позволило базе стать в один ряд с лучшими in-memory решениями. А с добавлением легковесного Write-Ahead Log и фоновых чекпоинтов мы сохраняем производительность на уровне 2.2 миллионов RPS, обеспечивая полную ACID-семантику и персистентность MVCC.
