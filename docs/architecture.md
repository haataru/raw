# Архитектура и Внутреннее Устройство

rawDB спроектирована как минималистичная, но экстремально быстрая колоночная база данных. В основе лежат принципы Lock-Free MVCC, Append-Only Storage и Memory-Mapped I/O.

## Слои архитектуры

rawDB организована в пять слоев, каждый с одной ответственностью:

1. **API Layer** (`rawdb.h`, `Database`, Python bindings) — точка входа для пользователя.
2. **Executor** — превращает распаршенный SQL в конкретные операции над Storage.
3. **Parser** — handwritten recursive-descent SQL парсер.
4. **Database** — владеет реестром таблиц, менеджером транзакций и координирует фоновые потоки.
5. **Storage** — физическое хранение таблиц, индексов и страниц в Mmap.

## Storage (Хранилище)

Каждая таблица (`Table`) инкапсулирует свое физическое представление на диске.

### Memory-Mapped I/O
Данные хранятся в бинарных `.raw` файлах. Доступ осуществляется напрямую через `mmap` (`MmapFile`), что избавляет нас от двойной буферизации (user-space / kernel-space) и делегирует кэширование страниц операционной системе.

### Колоночный Формат
Данные разделены на страницы по 64 KiB. Каждая страница содержит значения только одной колонки. Это радикально ускоряет выполнение аналитических `SELECT` запросов (особенно с агрегациями), так как в процессорный кэш загружаются только те данные, которые участвуют в запросе.

### VersionIndex и MVCC
Многоверсионность (Multi-Version Concurrency Control) реализована поверх колонок через `VersionIndex`.
- `VersionIndex` — это массив структур по 26 байт (содержащих `TxId` и цепочку версий).
- Читатели никогда не блокируют писателей. Операции чтения используют `shared_mutex`.
- Запись (`INSERT`, `DELETE`) эксклюзивна для таблицы, но благодаря `append-only` подходу и кешированию в памяти, она занимает микросекунды. `UPDATE` реализован как `DELETE` старой строки + `INSERT` новой.

## Журналирование (WAL) и Recovery

Для обеспечения ACID гарантий при скорости >2 млн RPS, rawDB использует:

### Write-Ahead Logging (WAL)
- `WalWriter` и `WalReader` управляют логом транзакций.
- Лог разбит на сегменты по 64 МБ (`wal_0000.log`, `wal_0001.log`).
- Каждая транзакция перед коммитом сериализует свои изменения в WAL и получает уникальный инкрементный LSN (Log Sequence Number).

### Fuzzy Checkpointing
Вместо Stop-The-World сбросов (которые убили бы пропускную способность), сырые данные сбрасываются на диск асинхронно:
1. Фоновый поток `Checkpointer` просыпается раз в 5 секунд.
2. Он делает асинхронный `msync` для грязных страниц и сохраняет B-Tree индексы.
3. Обновляется файл `checkpoint.meta` с номером последнего успешного LSN.
4. Безопасно удаляются старые сегменты WAL, что предотвращает переполнение диска.

При старте базы (`Database::open`), система читает `checkpoint.meta` и проигрывает только те WAL сегменты, которые были записаны после чекпоинта.

## Управление памятью и Garbage Collection

Поскольку данные append-only, удаленные строки помечаются как *tombstones* в `VersionIndex`.

- **Garbage Collector (GC)**: Фоновый поток, просыпающийся каждую секунду. Он определяет `cutoff` таймстемп (минимальный `TxId` среди всех активных транзакций) и физически зануляет/очищает ссылки на версии старше `cutoff`.
- Лимит очистки установлен на 500 MB/s, чтобы GC не мешал hot-path запросам.
- **VACUUM**: Ручная SQL команда `VACUUM table_name` сжимает базу, полностью освобождая место от удаленных строк и перенумеровывая `RowId`. Вакуум реализован без риска дедлоков через трехфазный протокол.
