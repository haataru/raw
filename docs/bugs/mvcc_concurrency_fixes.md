# Баги параллелизма MVCC и их исправления

В этом документе описаны три критических бага, связанных с параллелизмом и состоянием гонки (Data Race) в движке MVCC (Multi-Version Concurrency Control) базы данных `rawdb`. Эти баги приводили к потере данных и полному стиранию таблиц при экстремальных параллельных нагрузках (в частности, в `stress_test.cpp`).

## 1. Баг Snapshot Isolation (Чтение фантомов)

**Проблема**: 
В SQL-исполнителе была логическая ошибка при проверке видимости строки в текущем снимке транзакции (snapshot). В файлах `src/query/executor_mutate.cpp` и `src/query/executor_select.cpp` движок вызывал `search_version_index`, который возвращает тип `StatusOr<uint64_t>`. Для строк, вставленных *после* начала текущей транзакции, индекс корректно возвращал ошибку `Status::kNotFound` (в виде `std::unexpected`).

Однако проверка видимости была реализована так:
```cpp
if (!r || *r != Table::kNotFoundPage)
```
Поскольку `!r` возвращает `true` при наличии ошибки, движок ошибочно считал невидимые "будущие" строки видимыми. Это позволяло операции `DELETE` удалять абсолютно свежие вставки, которые даже не были до конца закомичены, разрушая изоляцию транзакций (Snapshot Isolation) и приводя к тому, что `stress_test.cpp` терял все свои строки.

**Исправление**:
Условие было исправлено. Теперь строка обрабатывается только если результат валиден И он не указывает на удалённую страницу:
```cpp
if (r && *r != Table::kNotFoundPage)
```

## 2. Глобальные состояния гонки (Data Race) в `VersionIndex`

**Проблема**:
Было выявлено два серьезных состояния гонки при доступе и изменении глобального индекса версий:

1. **Блокировки в `Table::commit_rows`**: Метод использовал `std::shared_lock lock(*rw_mtx);` во время выполнения `commit_rows`. Это позволяло нескольким потокам одновременно изменять отметки времени строк (`it->ts`). Что еще более критично, это позволяло одному потоку войти в `version_index_.commit_rows()`, который внутри вызывает `ensure_sorted()`. Метод `ensure_sorted()` перестраивает внутренний массив с помощью `std::sort`. Использование `std::shared_lock` приводило к тому, что один поток мог запустить `std::sort`, пока другой активно читал или обновлял элементы через `std::lower_bound`. Это приводило к сломанному поиску и потере коммитов.
2. **Сброс флагов в `VersionIndex::ensure_sorted`**: После завершения сортировки метод сбрасывал флаги синхронизации в неправильном порядке:
   ```cpp
   sorting_.store(false, std::memory_order_release);
   dirty_.store(false, std::memory_order_release);
   ```
   Из-за этого другой читающий поток мог проскочить ожидание `while (sorting_.load())`, увидеть, что данные все еще "грязные" (`dirty_ == true`), и ошибочно запустить *вторую* сортировку `std::sort` прямо в тот момент, когда первый читатель уже начал бинарный поиск `std::lower_bound`.

**Исправление**:
1. В `Table::commit_rows` слабая блокировка заменена на строгую `std::unique_lock lock(*rw_mtx);`. Это предотвращает любое параллельное чтение или сортировку, пока коммиты активно изменяют индекс.
2. Порядок операций с памятью в `ensure_sorted` изменен на правильный:
   ```cpp
   dirty_.store(false, std::memory_order_release);
   sorting_.store(false, std::memory_order_release);
   ```

## 3. "Призрачные строки" (Ghost Rows) - Потеря ожидающих коммитов

**Проблема**:
Для повышения производительности ввода-вывода метод `Table::insert` буферизирует до `kBatchSize` (8192) строк в памяти (в буфере `pending_`) перед их сбросом на диск и записью в `version_index_`. Находясь в этом буфере, строки помечаются идентификатором активной транзакции (`tx_id | kTxIdFlag`).

При успешном завершении транзакции `TransactionManager::commit` вызывал `Table::commit_rows(tx_id, commit_ts)`. Баг заключался в том, что `Table::commit_rows` обновлял *только* те строки, которые уже попали в `version_index_`. Он полностью игнорировал строки, все еще ожидающие в буфере `pending_`.

В результате, если транзакция коммитилась до переполнения и сброса своего батча, ее строки оставались в буфере `pending_` с временной меткой `tx_id`. Когда последующий запрос `SELECT` в конце концов принудительно сбрасывал буфер через `flush_pending()`, эти строки попадали в `version_index_` с меткой транзакции, которая уже завершилась. Поскольку ни одна активная транзакция больше не соответствовала этому ID, строки становились "призраками" — навсегда невидимыми для всех будущих запросов.

**Исправление**:
Метод `Table::commit_rows` был изменен: теперь он перехватывает массив `row_ids` и проверяет, принадлежат ли они буферу `pending_`:
```cpp
for (auto rid : row_ids) {
    if (rid >= pending_.start_rid && rid < pending_.start_rid + pending_.row_count) {
        pending_.row_ts[rid - pending_.start_rid] = commit_ts; // Прямое обновление в буфере
    } else {
        index_rows.push_back(rid);
    }
}
```
Теперь, если строка все еще ожидает в буфере, ее временная метка успешно обновляется на `commit_ts` прямо там, и в будущем она безопасно сбрасывается в глобальный индекс.
